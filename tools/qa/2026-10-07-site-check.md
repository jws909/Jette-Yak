# 사이트 전체 점검 — 2026-10-07

## 관리자 게시글 삭제 오류

`USERS.IS_ADMIN`의 실제 관리자 값은 문자 `Y`인데, 게시글 삭제 SQL이 숫자 `1`과 비교했다. Oracle이 `Y`를 숫자로 바꾸려다 `ORA-01722`가 발생했다.

- 수정: `UPPER(TRIM(is_admin))`으로 로그인 매퍼와 동일하게 관리자 값을 판별.
- 권한: 요청자가 전달한 관리자 플래그를 사용하지 않고, 로그인 사용자 번호로 DB의 관리자 여부를 확인.
- 삭제 방식: 게시글 상태를 `DELETED`로 변경. 댓글·첨부파일의 참조 행을 강제로 삭제하지 않음.
- 검증: 원래 조건의 오류를 SELECT로 재현했고, 수정 조건의 문자형·숫자형 관리자 및 일반 사용자 경우를 Oracle의 임시 SELECT 데이터로 확인. 실제 게시글 변경 없음.

관련 파일: `backend/src/main/webapp/WEB-INF/mybatis/mapper/community/community_mapper.xml`, `backend/src/test/java/com/app/community/CommunityDeletionCheck.java`.

## 다시 검사하는 방법

프런트 디렉터리에서 실행:

```powershell
npm test
npm run test:flows
npm run build
npm run lint
```

Tomcat에 새 코드를 반영한 다음 저장소 루트에서 실행. PowerShell 7 필요:

```powershell
pwsh -File tools/qa/readonly-http-check.ps1 -WithDemo
```

이 스크립트는 조회와 별도 체험 세션의 로그인·로그아웃만 수행한다. 게시글·약·사용자 정보를 저장하거나 삭제하지 않는다. 응답 원문과 사용자 정보도 출력하지 않는다.

Java의 기존 Check들은 `main` 메서드 기반이다. `mvn test-compile` 성공만으로 Check가 실행된 것은 아니다. 위 결과는 컴파일 뒤 해당 Check 클래스들을 각각 실행한 결과다. DB 의존 Check인 RegisteredGuideCheck, ManagementCheck, DurGuideCheck, CatalogCheck, ExpandedChatCheck는 실제 fixture·스키마 동작을 확인하지 않은 채 실행하지 않았다.

## 반영과 남은 확인

1. 이번 수정은 Eclipse Refresh·Clean/Publish·재시작 후 실제 HTTP 검사까지 완료. 이후 외부에서 소스를 수정할 때도 해당 반영 과정 확인.
2. 프런트는 한 번 새로고침. 여러 React 모듈을 동시에 교체한 기존 개발 탭은 이전 Context를 보관할 수 있음.
3. 관리자 계정으로 대상 게시글 삭제를 재확인. 이번 점검에서는 실제 사용자 게시글을 임의로 삭제하지 않았음.
4. 실제 메일 발송, OCR 업로드, 외부 Gemini 호출, 실제 계정·약 삭제는 실행하지 않았음. 화면 표시와 모의 요청 테스트로 실제 외부 서비스 성공까지 보장하지 않음.

### 확인된 기존 구조의 제한

- 가상 일정 ID의 `prescriptionId * 100000 + itemId * 10 + slot` 계산은 `itemId < 10000`을 가정한다. 실제 행 우선 처리는 보완했지만, 큰 itemId의 자리올림 충돌은 별도의 ID 체계 변경이 필요하다.
- 가족 삭제의 롤백은 모의 JDBC로 검증했고 실제 사용자 삭제는 시도하지 않았다. Oracle FK 메타데이터에서 `FK_MEAL_TIMES_USER`는 CASCADE, 커뮤니티 작성자·처리자 참조는 NO ACTION으로 확인했다. 가상 회원에게 해당 커뮤니티 참조가 있으면 관련 글을 임의로 지우지 않고 삭제 전체를 롤백한다.
- CORS 설정이 모든 origin의 credential 요청을 허용하고 있으며, 비밀번호는 기존 SHA-256 방식을 사용한다. 운영 환경의 origin 제한과 비밀번호 해시 이관은 별도 설정·데이터 이관 검토가 필요하다.
- 프로덕션 JS 청크가 500kB를 초과하는 빌드 경고가 남아 있다. 빌드 실패는 아니며, 페이지별 지연 로딩·청크 분리는 별도 성능 개선 대상이다.

PPT, 실제 사용자 데이터, DB 스키마, ignored 비밀 설정은 변경하지 않았다.
